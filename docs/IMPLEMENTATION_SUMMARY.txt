PIPELINE FLOW (File In → JSON Out)
================================================================================

Input: contract.pdf (or .docx, .txt)
  |
  v
[1] INGESTION (core/ingestion.py)
  ├─ pdfplumber / python-docx / plain read
  ├─ Normalize: strip headers/footers, rejoin hyphens, collapse whitespace
  └─ Output: normalized_text (canonical document)
  |
  v
[2] EXTRACTION (core/extraction.py)
  ├─ Regex matching: ^\d+(?:\.\d+)*\.?\s+
  ├─ Split on matches, extract clauses and cross-references
  ├─ Preserve char_start/char_end offsets (critical for hallucination-proof)
  └─ Output: List[Clause]
  |
  v
[3] CLASSIFICATION (core/classification.py)
  ├─ Keyword dictionary (indemnification, liability, termination, etc.)
  ├─ Substring match (case-insensitive)
  ├─ Append labels to each clause
  └─ Output: List[Clause] with labels
  |
  v
[4] CANDIDATE SELECTION (core/candidate_selection.py)
  ├─ Method 1: BM25 top-k scoring (text similarity)
  ├─ Method 2: Cross-reference pairing (xref resolution)
  ├─ Method 3: Type matrix (label pairs that conflict)
  ├─ Dedupe pairs, cap at ~30
  └─ Output: List[(clause_a, clause_b, ["bm25", "type_matrix", ...])]
  |
  v
[5] ANALYSIS (core/pipeline.py — STUB)
  ├─ Per-pair LLM call (stubbed: returns None)
  ├─ No findings generated (all pairs marked no_issue)
  └─ Output: List[Finding] (empty in v0)
  |
  v
[6] OUTPUT (core/__main__.py)
  ├─ JSON serialization (exact format of GET /runs/{id}/findings)
  ├─ Ranking: by severity then risk_score
  └─ Output: JSON (stdout or --output file)

DESIGN DECISIONS (Ponytail Mode)
================================================================================

1. No LLM Analysis in v0
   ├─ Reason: Integration matters more than accuracy at this stage
   ├─ Benefit: Surfaces schema/offset/type problems immediately
   ├─ Replacement: Stub returns None for all pairs
   └─ Next: Day 9 adds Claude API call

2. Keyword Classification Only
   ├─ Reason: 50 lines, catches type_matrix conflicts
   ├─ Accuracy: Will be wrong often (confidence=1.0 is honest)
   ├─ Benefit: Type matrix fires, finding candidates generates
   └─ Next: Week 5 adds LegalBERT fine-tuned on CUAD

3. BM25 (Naive TF-IDF)
   ├─ Implementation: O(n²) scoring, fast for ~50 clauses
   ├─ Ponytail: Good enough to surface structural problems
   ├─ Accuracy: Not optimized, ~30 candidate pairs kept per contract
   └─ Next: Week 6 upgrades to dense + hybrid retrieval

4. Type Matrix as YAML
   ├─ 20 lines, 6 label pairs defined (indemnification ↔ liability, etc.)
   ├─ Survives unchanged through v1 (no modification expected)
   ├─ Drives pair generation even if BM25 misses them
   └─ This is exactly how it scales to full taxonomy

5. No Database
   ├─ Reason: JSON on disk is a complete deliverable in v0
   ├─ Data shapes are final, so DB schema works day 1 without redesign
   ├─ Benefit: Runs locally, no DevOps overhead
   └─ Next: Week 11 adds PostgreSQL persistence

6. Single Smoke Test
   ├─ No per-function unit tests (YAGNI)
   ├─ One end-to-end test validates all layers
   ├─ Assertions: offsets resolve, stats consistent, no_issue counted
   └─ Any breakage shows up immediately (integration-first)
