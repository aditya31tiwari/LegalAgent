================================================================================
BY COMPONENT (Pipeline Layers)
================================================================================

LAYER 1: INGESTION
  File: core/ingestion.py
  Input: file_path (PDF, DOCX, TXT)
  Output: normalized_text
  Key function: ingest(file_path) → str
  Guarantee: Byte-identical on re-run

LAYER 2: EXTRACTION
  File: core/extraction.py
  Input: normalized_text
  Output: List[Clause]
  Key function: extract(text, contract_id) → List[Clause]
  Regex: ^\s*(\d+(?:\.\d+)*)\s*\.?\s+
  Features: char_start/char_end offsets, xref detection/resolution

LAYER 3: CLASSIFICATION
  File: core/classification.py
  Input: List[Clause]
  Output: List[Clause] (with labels)
  Key function: classify(clauses) → List[Clause]
  Method: Keyword dictionary (substring match)
  Confidence: 1.0 (keyword source)

LAYER 4: CANDIDATE SELECTION
  File: core/candidate_selection.py
  Input: List[Clause], config
  Output: List[(a_id, b_id, ["bm25", "type_matrix", ...])]
  Key function: select_candidates(clauses, config) → List[tuple]
  Methods: BM25 + xref + type_matrix
  Cap: ~30 pairs per contract

LAYER 5: ANALYSIS (STUB)
  File: core/pipeline.py (analyse_pair_stub)
  Input: Clause pair
  Output: Finding | None
  Status: STUB (returns None)
  Next: Replace with LLM call (Day 9)

ORCHESTRATION
  File: core/pipeline.py
  Key function: analyse(file_path, config) → (Run, List[Clause], List[Finding])
  Chains: ingestion → extraction → classification → candidate selection → analysis

================================================================================
DATA SHAPES (Reference)
================================================================================

class Clause:
  id: str                          # "acme_msa::5.2" (public ID)
  contract_id: str                 # "acme_msa"
  number: str | None               # "5.2", "(a)"
  heading: str | None              # Section title
  text: str                         # Full clause text
  char_start: int                  # Offset into normalized_text
  char_end: int                    # Offset into normalized_text
  ordinal: int                      # Document order
  labels: list[dict]               # [{"label": "...", "confidence": 1.0}]
  xrefs: list[dict]                # [{"raw": "...", "clause_id": "...", "resolved": bool}]

class Finding:
  id: str                          # Unique finding ID
  target_clause_id: str            # Primary clause
  related_clause_ids: list[str]    # Supporting clauses
  relation_type: str               # conflict | dependency | overlap | ambiguity | no_issue
  severity: str                    # low | medium | high
  risk_score: float                # 0.0 — 1.0
  rationale: str                   # Why they conflict
  surfaced_by: list[str]           # ["bm25", "type_matrix", "xref"]
  evidence: list[dict]             # [{"clause_id": "...", "start": 0, "end": 0}]
  refs: list[dict]                 # RAG sources (empty in v0)
  scores: dict                     # {"retrieval": 0.62, "confidence": 0.88}

class Run:
  id: str                          # "run_abc123"
  contract_id: str                 # "acme_msa"
  config: dict                     # {"retrieval_method": "bm25", "top_k": 5}
  stats: dict                      # {"clauses": N, "pairs": M, "findings": F, "no_issue": I}

================================================================================
COMMON QUESTIONS
================================================================================

Q: Where do char_start/char_end come from?
A: Ingestion stage produces normalized_text, then extraction stage records
   offsets into it. They are byte positions, validated by smoke test.

Q: Why is analysis stubbed?
A: Because Days 1–8 focus on integration, not accuracy. Stubbing surfaces
   structural problems (bad offsets, missing clauses) while they cost an
   afternoon to fix, not a week.

Q: What's the type_matrix?
A: A YAML dict mapping (label_a, label_b) → is_conflict. Example:
   ("limitation_of_liability", "indemnification") → True
   It drives candidate selection even if BM25 misses the pair.

Q: Can I add LLM analysis now?
A: Yes, replace analyse_pair_stub in core/pipeline.py with an LLM call.
   Keep the same signature: (Clause, Clause) → Finding | None.

Q: Where's the frontend?
A: Out of v0 scope. JSON on disk is the deliverable. Frontend comes week 13.

Q: Why no database?
A: Data shapes are final, so the schema works without redesign. JSON on disk
   is a complete deliverable. Add DB week 11.

Q: What's the BM25 implementation?
A: Naive TF-IDF score. Good enough for v0 to surface integration issues.
   Not optimized for accuracy (week 6 upgrades to dense + hybrid).
